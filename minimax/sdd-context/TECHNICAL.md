# 一页技术说明

本作品把“给工单列表添加状态筛选”的局部开发任务贯穿三项指定技术，用最小 CLI 完成规格驱动开发闭环。

**工程上下文。** `sdd_context.index` 将当前规格、待修改代码和测试存入独立 seekdb 实例。来源以相对路径和 SHA-256 标识，原文和用于检索的标准化文本同时保存。上下文由参数化 `MATCH ... AGAINST` SQL 的实际返回结果组成，附带原文行范围与版本哈希。每次完整导入替换旧快照，因此规格更新与文件删除会反映在后续查询中。若任务没有检索到必要资料类别，模块明确失败。

**跨运行状态。** `sdd_context.state` 调用真实 PowerContext Runtime 的 Scope 和 Memory 接口，将已完成事项、待办和验证结果写入持久化数据库。每次读写在独立 Python 进程中打开、操作和关闭 Runtime。后续 context 查询包含重新读出的状态和 Memory 引用，而不是只输出一份未被使用的日志。

**MiniMax 开发助手。** develop 入口把任务、seekdb 返回的当前资料和 PowerContext 已存状态组合为模型输入，通过 MiniMax 官方兼容 API 获取单文件修改。仅保存最终代码与响应元数据，不记录密钥或私有推理链。返回代码需通过语法和允许操作检查后才写入 after 快照。之后运行同一份目标及回归测试，保留命令、退出码、测试哈希与代码哈希。模型记录、前后快照与差异可以互相核对。

**验收边界。** 目标测试在修改前必须因缺少状态筛选而失败，原有回归必须通过；修改后同一组测试应全部通过。check_context.py 从空数据库执行真实 seekdb 检索、规格重新导入和 PowerContext 跨进程复用。replay.py 使用已保存的实际 MiniMax 修改重建验证流程，不要求模型重复生成完全一样的补丁。

MiniMax-M2.7 实际开发记录见 evidence/minimax-development.json，前后代码差异见 evidence/code.patch。作品的本地测试与复验日志随源码交付，正式比赛成绩仍以平台评审为准。
